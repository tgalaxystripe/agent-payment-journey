One lookup.
The answer is a route.

The journey The directory

An agent about to buy something knows one thing for certain: the merchant’s URL. The directory turns that into an answer to a single question — which routes to a paid order exist here?

The response has four capability slots. Today exactly one of them is populated.

Numbers on this page are read from the live advice store in the payability harness on 2026-09-17. The three unpopulated slots are named in the response contract; nothing fills them yet, so this page does not invent behaviour for them.

The question

A URL goes in

No account, no merchant ID, no integration on the merchant’s side. Just the address the agent was already headed to.

What the agent asks

inspect {
  "merchant_url": "https://www.westelm.com/cart?x=1"
}

One field. Nothing about the buyer, the cart or the amount goes with it, so the same call is safe to make before anyone has decided to buy anything.

Keyed on the merchant, not the URL

  • https://www.westelm.com/cart?x=1
  • http://westelm.com/ref=abc
  • WESTELM.COM:443/x#y

All three normalise to westelm.com and get the same answer under the same stable id, so the agent never has to guess a canonical spelling.

The answer

Four routes to a paid order, most direct first

The directory returns every route the merchant supports — it does not pick one. The agent takes the highest rung it can actually use, and drops to the next when a rung is empty.

  1. mcpthe merchant’s own tools

    The merchant exposes tools an agent can call directly. Nothing to read off a page, nothing to type into a form.

    Reserved slot — no behaviour is defined for it here yet.

    reserved
  2. machine_paymentspay without a card form

    A payment route built for machines: the merchant takes the payment directly, so there is no card form to find, fill or fight.

    Reserved slot — no behaviour is defined for it here yet.

    reserved
  3. provisioninga credential for this purchase

    A credential scoped to this merchant and this order, rather than a general payment method the agent has to be trusted with.

    Reserved slot — no behaviour is defined for it here yet.

    reserved
  4. browser_checkoutdrive the page, with a map

    No machine surface, so the agent works the site the way a person would — but carrying a playbook of what is actually on that checkout: where the guest path is, what the page prefills, which button lies.

    Person sets the spending cap, approves the amount, and takes the keyboard at login, captcha and card challenges. See what this rung is worth →

    772 domains
  5. { }no route known

    Every slot is empty. The agent has learned something useful anyway: this is not a merchant to improvise at.

    An unknown merchant is never an error — it comes back as a normal answer with nothing in it, so the agent can hand over cleanly instead of guessing.

    70 of 614

Only the fourth rung exists today, and the harness has already measured what it is worth: the same purchases run with that playbook in the prompt went from 20 of 28 to 24 of 28, and runs where the agent gave up went from 9 to 0. Every rung above it should beat it, because each one removes a page the agent has to interpret.

The person

Four moments a human is in the loop

These hold on every rung, populated or not — the route changes how the agent pays, not who is accountable for it. Quotes are from the policy every agent is given.

Before

Sets the bounds

One merchant, one cart, one amount, one credential — fixed before the agent starts.

“Use only the approved merchant, cart, amount, currency, and credential.”

At the total

Approves the spend

The agent asks for the exact amount once the total is known, and cannot pay until someone says yes.

“Never switch payment methods or repeat a declined or ambiguous submit.”

At a wall

Takes the keyboard

Sign-in, captcha, bot defence and card challenges are handed over rather than worked around.

“Hand login, captcha, WAF, and 3DS to the user.”

After

Is the only proof

The agent does not get to declare victory. Only the merchant’s own confirmation counts.

“Mark success only from merchant confirmation.”

Today

What the one populated rung actually covers

Across the 614 merchants on the target list. A separate 772 domains can be answered in total, because the advice stores reach past that list.

  • 462 walked — a real checkout probe ran
  • 82 inferred — classified, never walked
  • 70 no domain on file yet
  • Reproduced across two sessions76
  • Seen once only372
  • Contradicted on re-probe7
None of this is validated. Every record is a candidate: 398 of 537 are low confidence, 121 medium, 18 high. Most merchants were probed once, from one machine, at one moment — enough to show something was true, not that it stays true. Seven records were contradicted the second time they were checked. Advice built this way is a head start, not a guarantee, and the rungs above it are the actual fix.
